Let's discuss the approach to serialization.  

I think we should have a single abstraction layer for loading and saving game data, which can support multiple formats (YAML for static data, JSON for save/load).  
This abstraction layer would be responsible for converting between the in-memory data structures (WorldData, WorldObject, Actor, Behavior, etc.) and the serialized formats.  
This would allow us to keep the loading/saving logic separate from the core game logic, and also make it easier to switch out or add new serialization formats in the future if needed.

The player will have a username, and each game they create will have a player character name that is stored with the that save state.  
The player will also have a current level, progress in the game, gold, inventory (.etc) which will also be stored in the save state.  
I recommend that we have a single directory to store all game data, including the starting world data (NPC definitions, dialogue trees, item definitions, etc.) and the players save states.

There are 3 types of data we need to serialize:
1) Static data: this includes things like the world layout, NPC definitions, dialogue trees, item definitions, etc.  This data is read-only and will be loaded at the start of the game.  
We need a format like YAML for this, which is human-readable and easy to edit.
I suggest we use this filename template for static data: StaticData[data name].yaml.  
For example, StaticData[NPCDefinitions].yaml, StaticData[DialogueTrees].yaml, StaticData[ItemDefinitions].yaml, etc.
2) Dynamic save state data: this includes things like the current state of the world, the player's inventory, the NPCs' current modes and tasks, etc.  
This data is read-write and needs to be loaded once then saved during the game.  When the player starts a new game, we need to copy the game starting (default) data to the players 
save state.  Then we can load the players save state normally.  Assume we have one directory to store data, players save states should be prefixed with the , and any other files we need to persist.
We need a format like JSON for this, which is faster for machine parsing than YAML.
I suggest we use this filename template for dynamic data: [username]_[charactername]_[save timestamp].json.
For example, if the player is named "Alice" and their character is named "Warrior", their save state file might be named "Alice_Warrior_2024-06-01T12-00-00.json".
3) Starting world data: this includes the default state of the world when the player starts a new game.  This data is read-only and will be copied to the players save state when they start a new game.
We need a format like JSON for this, which is faster for machine parsing than YAML.
I suggest we use this filename template for starting world data: StartGameData[data name].yaml.
For example, if we have a default starting state that we want to copy to the players save state when they start a new game, we might name it StartGameData[InitialState].yaml.

  Phase 13 Serialization — Key Concerns, Tradeoffs, and Strategy

  The hard constraint you need to know first

  BehaviorRule.Trigger and BehaviorRule.ActionFactory are Func<SimContext, bool> and Func<SimContext, IActorTask>. InteractionEntry.Condition is another
  Func<>. These are compiled lambda closures — completely unserializable, by any format. The same applies to live IActorTask instances sitting in an
  ActionQueue.

  This one fact shapes the entire strategy. An NPC save file cannot be a serialized WorldObjectMoveable. It must be a template reference (which NPC type with
  what parameters) plus instance state (current position, HP, cooldowns). On load: reconstruct from the template in code, then overlay the saved state. The
  behavior wiring stays in C#.

  ---
  Your proposal — a few items to clarify

  Inconsistency in #3: You said "JSON format" for starting world data, then .yaml extension and the type name StartGameData[*].yaml. Which is it? My
  recommendation is YAML — starting world layout is authored content (content creators may want to edit it), and it's only loaded once at new-game creation, so
   parsing speed is irrelevant. JSON should be reserved for runtime-generated saves only.

  Bracket characters in filenames (StaticData[NPCDefinitions].yaml): Valid on Windows and Linux, but unusual and mildly risky in shell scripts and web paths.
  Consider underscores or dots instead: static_npc_definitions.yaml or StaticData.NPCDefinitions.yaml.

  ---
  The NPC template problem in detail

  Each NPC's ActorComponent is built by a template factory today (GuardTemplate.BuildGuardActor). For save/load to work:

  1. Assign every NPC a template ID at creation time and store it on the object (e.g., Actor.TemplateId = "Guard").
  2. Register an INpcTemplateFactory that maps (templateId, params) → WorldObjectMoveable (same code that lives in GuardTemplate today).
  3. Save file: { "templateId": "Guard", "params": { "patrolRadius": 4 }, "position": { "x": 10, "y": 5 }, "hp": 80, "mode": "Work", "cooldowns": {...} }
  4. Load: call factory → get a fully-wired NPC → apply overrides.

  If you rename a template, saves break. Mitigate: keep a stable templateId string separate from the C# class name, and add a migration table for renames.

  ---
  Dialogue tree serialization — the tricky part

  DialogueNode has four subtypes: Line, Choice, Pool, Sequence. YAML and JSON both need a type discriminator to deserialize polymorphic nodes. System.Text.Json
   supports this natively with [JsonPolymorphic] and [JsonDerivedType] in .NET 7+. YamlDotNet needs a custom type converter.

  DialoguePoolEntry.Requires and Forbids are Dictionary<string, MinMax> with OrdinalIgnoreCase comparer. The case-insensitive comparer won't round-trip through
   JSON by default — you'll need to reconstruct it on deserialization rather than serialize the comparer itself.

Domain mapping / DTO                                                                                                                                         
Yes — DTOs are just plain data classes designed to be serialization-friendly. Your shadow-property approach is the right call for this codebase. Simpler,      less ceremony, and keeps the serialization concern inside the class. The only place I'd push back is for types with many non-serializable members (like

---
What gets serialized

Agreed — full state. The key insight that simplifies this significantly: template state vs. runtime state:

- Template state — ReactiveRules, DialogueTree, Schedule, ShopComponent stock: NOT serialized. Comes from template reconstruction on load. The lambdas in
BehaviorRule.Trigger / ActionFactory are in this category — no serialization needed for them at all.
- Runtime state — ActionQueue, Mode, position, HP, inventory, cooldowns, faction rep, quest progress: IS serialized.

This eliminates the lambda problem for BehaviorRule. The only lambdas left to worry about are in SubTask.OnComplete, which leads to your point below.

---
Lambda serialization / MoveableActionsFactory

Your token + factory approach is exactly right, and it maps cleanly to what's already in the code. My proposed design:

ITaskToken        — serializable record: { TaskType, Priority, MaxTurns, ...task-specific params }
IActorTask        — adds: ITaskToken ToToken()
MoveableActionsFactory [Singleton] — maps task type name → Func<ITaskToken, IActorTask>

On save: queue.Select(t => t.ToToken()) → serialize list of tokens.
On load: factory.Create(token) → task.Begin(ctx) → enqueue.

The key question is mid-execution state: TurnsElapsed, CurrentSubTaskNode position, TurnsRemainingInCurrentSubTask. For tasks like WanderTask (which doesn't
use SubTasks at all — it overrides TickNoSubTasks), the only interesting mid-execution state is _ticksUntilNextWaypoint. For SubTask-based tasks, restarting
from Begin() is fine — the player won't notice. I'd recommend: restart all tasks from tick 0 on load for now, and only add mid-subtask restoration later if
specific tasks need it. The tokens just need to capture constructor parameters.

For _ticksUntilNextWaypoint and similar private runtime fields: include them in the token as optional, and add an internal Restore(ITaskToken) method to the
task. Not required for v1.

NPC template problem

Your approach is sound. The one open question: what identifier maps saved state back to the template NPC? I'd suggest adding a TemplateKey string property to

1. Build world from templates (each NPC has its TemplateKey)
